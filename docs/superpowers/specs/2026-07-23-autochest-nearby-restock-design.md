# AutoChest 附近容器双向补货设计

## 1. 背景与目标

AutoChest 是面向 Paper 1.21.4、Java 21 的新建 Maven 插件。它提供类似泰拉瑞亚的附近容器快捷整理能力：

- `/autochest deposit`：将玩家主背包中的物品快速堆叠到附近已有同类物品的箱子或木桶中。
- `/autochest restock`：从附近箱子或木桶取出同类物品，补满玩家主背包和快捷栏中的现有堆叠。
- `/ac` 作为主命令别名。

设计优先保证 Paper 线程安全、物品数量守恒、保护插件兼容和主线程性能。

## 2. 已确认的行为

### 2.1 搜索范围

- 以命令执行瞬间的世界 UUID 和方块坐标为固定中心。
- 默认扫描 X、Y、Z 各正负 8 格，即最多 `17 × 17 × 17 = 4913` 个方块；范围可配置。
- Y 范围裁剪到世界合法高度，范围体积以 `long` 校验溢出。
- 只扫描任务开始时已加载的区块；不主动加载区块或添加区块票。
- 容器总数不设置人为上限。
- 玩家在同一世界移动不会改变扫描中心。
- 监听 `PlayerQuitEvent`、`PlayerChangedWorldEvent` 和 `PlayerDeathEvent`；任一事件发生时立即使玩家当前任务的 session epoch 与 token 失效，因此重连、返回原世界或重生都不能恢复旧任务。
- 每次提交前还要检查玩家在线、仍在初始世界且 `isDead()` 为 false。

### 2.2 参与容器与顺序

- 支持普通箱子、陷阱箱和木桶。
- 双箱规范化为一个逻辑库存并去重。
- 按初始扫描中心到容器几何中心的平方欧氏距离从近到远处理。
- 距离相同时按规范化容器坐标键稳定排序，容器内部按槽位升序处理。

### 2.3 物品匹配

- 最终匹配使用主线程实时 `ItemStack#isSimilar()`，要求材料和完整 ItemMeta 一致。
- 名称、Lore、附魔、耐久、药水数据等不同的物品不会混合。
- 异步阶段仅使用主线程生成的数量归一化物品身份快照建立候选索引；该索引不能替代提交时的实时判断。

### 2.4 存入规则

- 仅处理玩家主背包槽位 `9..35`，不操作快捷栏、盔甲栏或副手。
- 对每种物品独立执行全局两阶段存入：
  1. 遍历全部候选容器，优先补满其已有同类未满堆叠。
  2. 若仍有剩余，再遍历相同候选容器并使用其空槽。
- 一个容器只有在任务快照与提交时均仍含至少一个同类物品时，才可成为该物品的候选容器并在第二阶段使用空槽。
- 空箱不会因为其他箱子存在同类物品而获得接收资格。
- 示例：玩家存入 60 个圆石，距离顺序为 A、B、C，现有堆叠分别是 5、64、8。先向 A 放入 59，再向 C 放入 1，结果为 64、64、9，不使用空槽。

### 2.5 补货规则

- 处理玩家快捷栏与主背包槽位 `0..35`。
- 只补充任务开始时已经存在的非满堆叠；命令接受时将槽位编号、初始物品身份和最大堆叠数记录为不可变目标白名单。
- 监听玩家库存交互，并在每个提交点比较白名单与实时槽位；目标槽位一旦变为空或变成其他物品，就永久失去本次任务的补货资格，即使之后放回同类物品也不恢复。
- 按玩家槽位升序，将每个槽位补至该物品自身最大堆叠数；全局排序优先级固定为“玩家槽位 → 容器距离 → 容器槽位”，稀缺库存不得先分配给更高序玩家槽位。
- 不使用玩家空槽，不创建新物品种类或额外堆叠。
- 从候选容器按距离和容器槽位顺序取物。

## 3. 命令、权限与冷却

- `/autochest deposit`：权限 `autochest.deposit`，默认所有玩家拥有。
- `/autochest restock`：权限 `autochest.restock`，默认所有玩家拥有。
- `/autochest reload`：权限 `autochest.reload`，默认仅 OP；控制台只允许使用 reload。
- 同一玩家同时最多有一个任务；任务进行中再次执行任一操作命令会被拒绝。
- `deposit` 默认独立冷却 5 秒，`restock` 默认独立冷却 3 秒，均可配置。
- 冲突检查先于冷却检查；成功取得任务锁并接受任务后立即记录对应冷却。
- 冷却一经消费不因无匹配物品、玩家取消、Hook 查询失败、异步拒绝或内部错误而退还，以防反复触发范围扫描。
- 冷却使用单调时间源，避免系统时间调整影响结果。

## 4. 总体架构

采用“异步候选规划、主线程逐容器实时重算”方案：

1. 主线程校验命令、权限、任务冲突和冷却，并为玩家创建带唯一 token 的任务。
2. 主线程以方块数和纳秒时间双预算分 tick 扫描范围。
3. 主线程识别容器、规范化双箱、执行 Hook，并创建玩家和容器库存快照。
4. 插件私有有界线程池仅处理不含实时 Bukkit 对象的 DTO，完成稳定排序、物品索引和候选关系规划。
5. 返回主线程后按已确认语义执行实时提交：
   - `deposit` 先对全部候选容器执行 `FILL_EXISTING` 完整遍历，再对全部候选容器执行 `USE_EMPTY` 完整遍历；不能在单个容器内提前进入空槽阶段。
   - `restock` 以玩家目标槽位为外层顺序，再按容器距离与容器槽位寻找来源，确保低序槽位优先补满。
6. 每次遍历中的每个容器都重新检查玩家状态、双箱两半区块、容器结构、Hook 和实时库存，再以独立小事务提交；成功后更新任务账本。
7. 完成、取消或失败后释放任务锁，并在主线程发送聊天反馈和音效。

异步结果只是候选提示，永远不是库存事实来源。所有世界读取、库存读取、Hook 查询、最终相似性判断和库存写入都在主线程完成。

## 5. 组件职责

### 5.1 启动与配置

- `AutoChestPlugin`：初始化配置、命令、任务注册表、扫描调度器、Hook 和私有线程池；禁用时取消任务并关闭资源。
- `AutoChestConfig`：解析范围、每 tick 扫描预算、提交预算、冷却、消息和音效，并对空值、类型错误、负数、过大范围及无效枚举采用安全默认值。
- reload 只影响之后创建的任务；运行中的任务使用创建时配置快照。

### 5.2 命令与任务生命周期

- `AutoChestCommand`：处理 `deposit`、`restock`、`reload` 和帮助信息。
- `PlayerTaskRegistry`：使用玩家 UUID、任务 token、玩家 session epoch 和插件 generation 管理唯一运行任务；退出、换世界或死亡事件会立即递增 session epoch 并使旧任务永久失效。
- `CooldownService`：分别维护两种操作的冷却。
- `PlayerLifecycleListener`：监听 `PlayerQuitEvent`、`PlayerChangedWorldEvent` 和 `PlayerDeathEvent`，只负责使当前任务失效，不长期保存 Player 引用。
- `RestockTargetListener`：监听会改变玩家库存的点击、拖拽、拾取、丢弃等事件，为运行中的 restock 任务标记发生变化的目标槽位；提交时仍以实时比较作为最终判定。
- 迟到异步回调必须同时验证玩家任务 token、session epoch 和插件 generation，不能操作或释放新任务。

### 5.3 扫描与快照

- `NearbyContainerScanner`：按双预算分 tick 枚举坐标，只读取已加载区块。
- `ContainerIdentity`：规范化单箱、双箱和木桶身份，用于去重与稳定排序；双箱身份保存两半坐标，任何方块、状态或库存读取前必须确认两半所在区块都已加载。
- `InventorySnapshotFactory`：在主线程创建深拷贝快照，并转换为 Bukkit-free DTO。

### 5.4 Hook 策略

公共接口 `ContainerAccessPolicy` 不暴露任何第三方类型。三个适配器均为可选依赖，Maven scope 使用 `provided`，`plugin.yml` 使用 `softdepend`。

- `WorldGuardHook`：目标位置存在任意非 `__global__` 区域时排除该容器，不考虑成员、bypass 或旗标；双箱任意一半位于区域内即排除。
- `TownyHook`：通过目标 Towny 版本的官方 API，按玩家、位置、目标方块和 `ActionType.SWITCH` 的地块权限语义判断；不自行推导居民、好友或城镇关系。
- `ChestShopHook`：通过官方商店识别 API；若目标版本没有稳定 API，则使用隔离的窄反射适配层。商店箱一律排除，双箱任意一半为商店箱即排除。
- 插件未安装时不启用对应 Hook。
- 若服务器已安装任一目标插件，但对应适配器初始化失败，则禁用 `deposit` 与 `restock` 并整体拒绝新任务，明确提示保护检查不可用；管理员修复依赖并成功 reload 或重启后方可恢复。
- 已初始化 Hook 在单个容器查询时抛出异常或结果无法确认，则保守排除该容器并限频记录日志。
- 扫描时和每次提交前都执行 Hook；双箱必须分别查询两半并按任一拒绝聚合；提交事务写入期间不调用第三方 API。

## 6. 线程与性能模型

- Bukkit/Paper 世界、方块、库存、玩家和 Hook API 只在主线程访问。
- 扫描同时受“每 tick 最大方块数”和“每 tick 最大纳秒数”约束，默认方块预算建议为 512。
- 提交阶段也按每 tick 容器数和纳秒时间预算让出主线程，避免容器密度高时形成长 tick；预算只允许在容器事务之间检查，一旦事务开始，必须在同一次不可让出的主线程调用中完成提交或恢复。
- 异步 DTO 仅包含 UUID、世界 UUID、整数坐标、规范化容器键、距离、槽位、数量、最大堆叠数及复制后的身份字节，不保存 `Player`、`World`、`Block` 或 `Inventory`。
- 使用插件私有的固定大小、有界队列 Executor，不使用 common pool。队列满时拒绝新任务并反馈服务器繁忙。
- 插件禁用时 generation 失效，停止接收任务，取消调度任务并关闭 Executor。
- 玩家在线与任务有效性在扫描 tick、快照前、异步提交前后、每个容器重验和每个事务提交前检查；校验包含 token、session epoch、generation、在线状态、初始世界 UUID 与 `isDead()`。

## 7. 实时提交与一致性

每个容器事务在主线程的单次不可让出调用中执行：

1. 通过 UUID 重新取得玩家，检查在线、非死亡、初始世界 UUID、任务 token、session epoch 和 generation。
2. 对单箱或木桶确认对应区块仍已加载；对双箱先确认两半区块均已加载，再读取两半方块状态，并验证规范化身份与逻辑库存结构仍一致。
3. 对容器的每个组成方块重新执行三个 Hook，任一拒绝则跳过整个逻辑容器。
4. 读取玩家与容器实时槽位后立即 `clone()`；业务计算不得对 `Inventory#getItem()` 返回的引用调用 `setAmount()`，before-image 和 after-image 都只能由深拷贝构造。
5. 使用实时 `ItemStack#isSimilar()` 验证候选，并根据实时来源数量、目标容量、restock 不可变槽位白名单和任务剩余需求重新计算移动量。
6. 在内存中构造完整 after-image，验证同类物品移动前后总数守恒、数量非负且不超过槽位上限。
7. 提交采用来源先扣、目标后增的固定顺序；在全部相关槽位写入完成前不得按时间预算让出到下一 tick。
8. 写入后逐槽复核当前值与 after-image 一致，成功后才更新统计和任务账本。
9. 任一写入或复核失败时执行 compare-and-verify 恢复：仅当槽位仍等于本事务已写入的 after-image 时才恢复对应 before-image，避免覆盖外部新变化。
10. 恢复后再次逐槽复核并计算来源与目标总量；若无法完整恢复，立即终止任务，并记录容器坐标、槽位、物品身份及恢复前后数量的高严重度审计日志。

某个容器在重验时已失效、保护状态变化或槽位不再匹配时，跳过该容器或对应候选，不为其保留额度；后续容器继续依据实时状态处理。

一致性保证属于正常服务端运行中的最佳努力事务，不承诺抵御 JVM 崩溃、强制终止进程或其他插件违规异步写库存。

## 8. 玩家反馈

- 命令接受后立即发送“正在扫描附近容器”聊天消息。
- 成功时报告移动物品总数、实际参与容器数和跳过容器数，并播放成功音效。
- 无匹配物品、冷却中、任务冲突、服务器繁忙、取消和内部失败使用独立聊天消息与音效。
- 消息前缀、文本和音效均可配置。
- 所有玩家消息与声音均在主线程执行。

## 9. 错误与边界处理

- 配置缺失、类型错误、空字符串、负值、超范围值和无效音效均回退至安全默认值并输出明确警告。
- 玩家退出、换世界或死亡时由事件监听器立即永久取消任务；同世界移动不取消。
- 区块卸载、容器破坏或双箱变化只跳过失效容器。
- Hook 失败采用保守拒绝，不回退到无保护访问。
- 异步规划拒绝、超时或抛出异常时，不执行库存写入并安全结束任务。
- 冷却、任务锁和异步回调均以 UUID 管理，不长期持有 Player 引用。

## 10. 验证计划

使用 JUnit 5 测试纯规划、排序、冷却和事务逻辑；使用 Mockito 与兼容 Paper 1.21.4 的 MockBukkit 版本测试主要 Paper 交互。若 MockBukkit 无法覆盖第三方插件 API，则使用适配器接口假实现测试聚合策略，并在真实测试服务器完成集成验证。

自动化测试至少覆盖：

- deposit 两次完整容器遍历：全局先填已有堆叠、再使用候选容器空槽，且第二阶段重新验证实时接收资格。
- 圆石 `5 / 64 / 8` 与存入 `60` 的验收示例。
- 物品元数据不同时不匹配。
- restock 仅补满命令接受时记录的不可变目标槽位，不使用空槽；目标槽位一旦变化，即使放回同类物品也不恢复资格。
- restock 稀缺来源按“玩家槽位 → 容器距离 → 容器槽位”分配。
- 双箱去重、跨区块两半加载检查、距离排序及同距稳定排序。
- 玩家退出后重连、换世界后返回、死亡后重生、区块卸载、容器破坏和快照过期。
- 重复命令拒绝、两种独立冷却及命令接受后不退还冷却。
- WorldGuard 区域排除、Towny 权限允许/拒绝、ChestShop 商店箱排除。
- Hook 缺失、初始化失败时拒绝整个任务，以及运行期查询异常时排除单个容器。
- clone-only after-image、来源先扣目标后增、事务不可跨 tick、compare-and-verify 恢复与物品数量守恒。
- 插件禁用后迟到回调不能修改库存或释放新任务锁。

Paper 1.21.4 人工验收覆盖单箱、双箱、木桶、多玩家竞争、漏斗变化、三个实际 Hook 插件、大量容器、配置 reload 和插件禁用场景。
